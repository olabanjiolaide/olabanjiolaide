The problem

A single category can be useful for a clear support request. It becomes less useful when a message combines goals, supplies background information, or leaves the actual problem unclear. A high score on templated validation data does not establish that these cases are handled reliably.

The engineering task is to make suggestions inspectable, preserve what the model originally predicted, and keep human confirmation separate from classification and resolution.

My contribution

I develop the project across data preparation, model experiments, prediction serving, and the review interface. The work includes input validation, duplicate-aware splits, checked model bundles, tests, saved-request management, and evidence-based review.

I completed a 40-case assisted review pilot and used the documented failures to guide the next development steps. The pilot labels were reconciled with assistant support; they are not independently adjudicated ground truth.

Engineering decisions

Reproducible baseline
Pinned source downloads, checksums, preparation manifests, and a TF-IDF/logistic-regression baseline make the initial experiment traceable.
Human review stays explicit
Suggestions, editable drafts, confirmation, and saving are distinct states. Corrections retain the original prediction; saved requests include notes, status, and history.
Evidence comes from the message
For optional local-model needs proposals, Python assigns source-fragment IDs. The model assigns those IDs; the server reconstructs the original text and validates coverage and relationships.
Failed candidates stay offline
Experiments that regress on known probes are documented rather than promoted on the strength of a synthetic-validation gain.

Results and limitations

The original synthetic-source validation macro-F1 is 0.9984, with possible template overlap. It is not a production accuracy estimate. The source held-out test has not been evaluated.

Frozen semantic-plus-scope policy on 40 assisted development cases
Request typeObserved outcome
24 single-intent requestsAll received a suggestion; 20 were correct.
8 unsupported requestsAll 8 were withheld.
4 multiple-intent requestsOnly 1 was withheld; 3 still received a single category.
4 insufficient-context requestsOnly 2 were withheld.

These counts expose remaining ambiguity failures. They do not establish general reliability, statistical significance, or an effective ambiguity detector. Individual review records remain private.

The newer numbered-evidence proposal path has authored regression and contract tests. Live Qwen generation was not run in its implementation workspace, so no live accuracy or latency improvement is claimed. A valid evidence structure can still contain a wrong interpretation.

What comes next

Measure the complete review workflow: generation wait, navigation, correction effort, save/reload success, and failures. Compare model changes on the same examples and runtime budget before expanding the interface further. A saved review alone is not evidence that the interpretation is correct.

The app runs locally. Optional semantic and Ollama modes need separate setup. No customer operations are executed by the review controls.
